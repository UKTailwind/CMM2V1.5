=== BLIT READ [#]b, x, y, w, h [,page]
or
BLIT WRITE [#]b, x, y [,orientation]
or
BLIT CLOSE [#]b
---
Copy one section of the display screen to or from a memory buffer.
BLIT READ will copy a portion of the display to the memory buffer ‘#b’.  The source coordinate is ‘x’ and ‘y’ and the width of the display area to copy is ‘w’ and the height is ‘h’.  When this command is used the memory buffer is automatically created and sufficient memory allocated.  If the buffer is already in use and the new area has the same width and height the new area overwrites the stored one (a different size is an error).  The optional ‘page’ specifies which page is to be read; the default is the current write page.  Set ‘page’ to FRAMEBUFFER to read from the framebuffer (see the FRAMEBUFFER command).
BLIT WRITE will copy the memory buffer ‘#b’ to the current write page.  The destination coordinate is ‘x’ and ‘y’ using the width and height of the buffer.  The optional ‘orientation’ parameter (0 to 7) defaults to 4 and specifies how the stored image data is changed as it is written out.  It is the sum of the following values:
{l=720}&B001 = mirrored left to right
{l=720}&B010 = mirrored top to bottom
{l=720}&B100 = don't copy transparent pixels
BLIT CLOSE will close the memory buffer ‘#b’ to allow it to be used for another BLIT READ operation and recover the memory used.
Notes:
{n=39 v=0}Sixty four buffers are available ranging from #1 to #64.  They are the sprites: BLIT and SPRITE are the same command, so a buffer read with BLIT READ can be shown with SPRITE SHOW and every SPRITE command can also be written as BLIT (see SPRITE).
{n=39 v=0}When specifying the buffer number the # symbol is optional.
{n=39 v=0}All other arguments are in pixels.
{n=39 v=0}A transparent pixel is one whose stored value is zero: black in the 4, 8 and 16-bit colour depths, and the colour 0 (black with a transparency of 0, which RGB(0,0,0) is not) in the 12 and 32-bit colour depths.

=+= BLIT x1, y1, x2, y2, w, h [,page] [,orientation]
---
Copy one section of the display screen to another part of the display.
The source coordinate is ‘x1’ and ‘y1’.  The destination coordinate is ‘x2’ and ‘y2’.  The width of the screen area to copy is ‘w’ and the height is ‘h’.
‘page’ is the page number that the image data is read from; it is then written to the current write page as specified by the PAGE WRITE command.  If ‘page’ is omitted the data is read from the write page.  Set ‘page’ to FRAMEBUFFER to read from the framebuffer (see the FRAMEBUFFER command).
All arguments are in pixels and the source and destination can overlap.  The area is clipped to the source and destination pages.
The optional ‘orientation’ parameter (0 to 7, default 0) specifies how the section of the screen is changed as it is copied.  It is the sum of the following values:
{l=720}&B001 = mirrored left to right
{l=720}&B010 = mirrored top to bottom
{l=720}&B100 = don't copy transparent pixels (see the notes above)

=+= BLIT FRAMEBUFFER from, to, xin, yin, xout, yout, width, height [,colour]
---
__IN THE 4-BIT COLOUR DEPTH ONLY__ Copies an area of the framebuffer ‘from’ to the framebuffer ‘to’, as on the PicoMite.  ‘from’ and ‘to’ are each N, L, F, 2 or T (a framebuffer that has not been created is N, the display: see the FRAMEBUFFER command) and must be different.
‘xin’ and ‘yin’ define the top left of the area of ‘width’ and ‘height’ on the source framebuffer to be copied, which must be within it.  ‘xout’ and ‘yout’ define the top left of the area on the target framebuffer to receive the copy; the copy is clipped to the target.
The optional parameter ‘colour’ defines a pixel colour on the source which will not be copied.  If omitted (or -1) all pixels are copied.  The colour is specified as a number between 0 and 15 representing:\nBlack, Blue, Myrtle, Cobalt, Midgreen, Cerulean, Green, Cyan, Red, Magenta, Rust, Fuchsia, Brown, Lilac, Yellow and White

# ImageSlots.c BlitFlash: 15 or 17 arguments; slots 1-3 give "Flash image slots are not provided: use slots 4 to 8";
# 'to' is Rgb121Letter (in a non-4-bit depth N, L, F, 2, T are pages 0-4) or a page number 0 to MM.INFO(MAX PAGES);
# "Frame buffer 2 not created" for 2 in a 4-bit mode without it; the source area must be within the image.
=+= BLIT FLASH n, to, xin, yin, xout, yout, width, height [,colour]
---
Copies an area of the image held in image slot ‘n’ to a framebuffer or a page, as the PicoMite's BLIT FLASH does.  ‘n’ is 4 to 8: the image slots are loaded with FLASH LOAD IMAGE (see Image Slots in the chapter Video Modes and Pages).
‘to’ is a framebuffer N, L, F, 2 or T, or a page number.  In a 4-bit mode a framebuffer that has not been created is N (but 2 is then an error); in the other colour depths N, L, F, 2 and T are the pages 0, 1, 2, 3 and 4.
‘xin’ and ‘yin’ define the top left of the area of ‘width’ and ‘height’ on the image to be copied, which must be within the image.  ‘xout’ and ‘yout’ define the top left of the area on the target to receive the copy; the copy is clipped to the target.
The image's pixels are the PicoMite's 16 colours, drawn in the colour depth of the target.  The optional parameter ‘colour’ defines a pixel colour in the image which will not be copied.  If omitted (or -1) all pixels are copied.  The colour is specified as a number between 0 and 15 representing:\nBlack, Blue, Myrtle, Cobalt, Midgreen, Cerulean, Green, Cyan, Red, Magenta, Rust, Fuchsia, Brown, Lilac, Yellow and White

# sprites.c blitother MEMORY: at least 5 arguments; drawn through DrawBuffer (any colour depth) on the write page,
# clipped to HRes and VRes; the nibbles stream on from row to row (no padding); the low nibble first.
=+= BLIT MEMORY address, x, y [,colour]
---
Draws an image held in memory as a packed array of colour nibbles on the current write page, with its top left at ‘x’, ‘y’; the image is clipped to the screen.  Each nibble is one of the PicoMite's 16 colours, a number between 0 and 15 representing:\nBlack, Blue, Myrtle, Cobalt, Midgreen, Cerulean, Green, Cyan, Red, Magenta, Rust, Fuchsia, Brown, Lilac, Yellow and White
The first word of the area of memory starting at ‘address’ must contain the width and height of the image as 16-bit integers with the width as the bottom 16 bits.  The pixels follow, two to a byte with the left pixel in the low nibble, each row following on from the one before.
If the optional parameter ‘colour’ is specified then pixels of that colour are not drawn (-1 draws them all).
If the top bit of either the width or height is set to 1 then the colour data is treated as compressed (the remaining 15 bits are used as the width and/or height).  The compression algorithm is simple: each byte contains a count in the bottom nibble (1-15) and a colour in the top nibble (0-15).  In the event that more than 15 pixels are the same colour additional bytes are used for that colour.

=== SPRITE
--- keep
The SPRITE commands are used to manipulate small graphic images on the screen.  These are useful when writing games.  See Appendix F for how sprites, their layers and their collisions work, and the SPRITE() functions for interrogating them.
SPRITE is another name for BLIT: every SPRITE command can also be written as BLIT and every BLIT command as SPRITE (a program lists them all as BLIT).  The sprites are the buffers #1 to #64 that BLIT READ also uses, and the # before a sprite number is optional.
A sprite can be up to the size of the screen.  Its transparent pixels (see BLIT) are not drawn, so that the background shows through them.  A sprite is held in the pixel format of the colour depth set by MODE when it was loaded: after a MODE command that changes the colour depth close the sprites (SPRITE CLOSE ALL) and load them again.

=+= SPRITE CLOSE [#]n
--- keep
Closes sprite ‘n’ and releases its memory resources allowing the sprite number to be re-used.  If the sprite is displayed it is first removed and the stored background replaced.  The command will give an error if other sprites are copied from this one unless they are closed first.

=+= SPRITE CLOSE ALL
--- keep
Closes all sprites and releases all sprite memory.  The screen is not changed.

# sprites.c COPY: the new numbers must be free ("Buffer already in use"), a copy cannot be copied ("Can't copy a copy").
=+= SPRITE COPY [#]n, [#]m, nbr
--- keep
Makes a copy of sprite ‘n’ to ‘nbr’ of new sprites starting at number ‘m’.  Copied sprites share the same loaded image as the original to save memory.  The new sprite numbers must not be in use, and a copy cannot itself be copied.  While copies exist the original cannot be closed or read into.

=+= SPRITE HIDE [#]n
--- keep
Removes sprite ‘n’ from the display and replaces the stored background.  To restore a screen to a previous state sprites should be hidden in the opposite order to which they were written ("LIFO").

# b14 lists SHOW (SAFE), HIDE (SAFE, ALL), SWAP, MOVE, SCROLLR and SCROLL as unusable while the sprites are hidden. The
# code (sprites.c, hideall) refuses SHOW, SHOW SAFE, HIDE ALL, HIDE SAFE, SWAP, MOVE, SCROLLR, SCROLL and also CLOSE with
# "Sprites are hidden", but not plain HIDE, which then draws the stored background again: a missing check (code bug).
# The entry lists HIDE with the others, as b14 does: fix the code (HIDE: if(hideall)error("Sprites are hidden")).
=+= SPRITE HIDE ALL
--- keep
Hides all the sprites allowing the background to be manipulated.  SPRITE RESTORE shows them again.
While the sprites are hidden SPRITE SHOW, SHOW SAFE, HIDE, HIDE SAFE, HIDE ALL, SWAP, MOVE, SCROLL, SCROLLR and CLOSE must not be used (they give the error "Sprites are hidden").

=+= SPRITE HIDE SAFE [#]n
--- keep
Removes sprite ‘n’ from the display and replaces the stored background.  Automatically hides all more recent sprites as well as the requested one and then replaces them afterwards.  This ensures that sprites that are covered by other sprites can be removed without the user tracking the write order.  Of course this version is less performant than the simple version and should only be used if there is a risk of the sprite being partially covered.

=+= SPRITE INTERRUPT sub
--- keep
Specifies the name of the subroutine that will be called when a sprite collision occurs.  See Appendix F for how to use the SPRITE() functions to interrogate details of what has collided.

=+= SPRITE LOAD fname$ [,start_sprite_number]
---
Loads the file ‘fname$’ which must be formatted as an original Colour Maximite sprite file.  If an extension is not specified “.SPR” will be added to the file name.
The first line of the file holds the width of the sprites and their number, and optionally their height (the width if it is omitted), separated by commas: eg, `16, 8` or `16, 8, 24`.  Each sprite follows as ‘height’ lines of ‘width’ characters, a character for each pixel:
{l=720}space = transparent
{l=720}0 = black, 1 = blue, 2 = green, 3 = cyan, 4 = red, 5 = magenta, 6 = yellow, 7 = white
{l=720}8 = light grey, 9 = grey, A = orange, B = pink, C = gold, D = salmon, E = beige, F = brown
Any other character is also transparent, a short line is filled out with spaces, and lines starting with an apostrophe (') are comments.
The sprites are loaded as the sprite numbers from ‘start_sprite_number’ (1 if it is omitted) on.  Multiple sprite files can be loaded by specifying a different ‘start_sprite_number’ for each file.  The programmer is responsible for making sure that the sprite numbers used by the files do not overlap.

# sprites.c loadarray: parsenumberarray (integer or float), at least w x h elements ("Array Dimensions"), w 1 to
# MM.HRES, h 1 to MM.VRES, "Buffer already in use" if n is loaded.
# Suspected CODE BUG: in a 12-bit mode convert_12bit keeps only the RGB bits, so every pixel has a transparency of 0
# (the LOAD and LOADPNG paths OR in 0xF000): the sprite may not show. Check on the board and fix in the code.
=+= SPRITE LOADARRAY [#]n, w, h, array%()
--- keep
Creates the sprite ‘n’ with width ‘w’ and height ‘h’ by reading w × h RGB888 colour values from ‘array%()’ (an integer or floating point array).  The values must be stored in order of columns across and then rows down starting at the top left.  Black pixels are transparent.
This allows the programmer to create simple sprites in a program without needing to load them from disk or read them from the display.  The firmware will generate an error if ‘array%()’ is not big enough to hold the number of values required, or if sprite ‘n’ is already in use.

# b14: "If the file is in RGB888 format then an RGB level of 0,0,0 is used to determine transparency". The code (upng.c,
# as the PicoMite's decoder was brought in) expands RGB, grey and indexed files to RGBA with an alpha of 255, so loadpng
# sees format 3 (RGBA8) for every file and an RGB file loads with every pixel solid (black as NOTBLACK). The entry
# follows the code. A regression from b14 that old programs may notice: restore it in the code if it matters.
# Size: "Image too large" if width >= MM.HRES or height >= MM.VRES. 32-bit depth: the alpha is copied, no cut-off.
=+= SPRITE LOADPNG [#]n, fname$ [,transparency_cut_off]
---
Loads the PNG image ‘fname$’ as sprite number ‘n’, which must not be in use.  If an extension is not specified “.PNG” will be added to the file name.  The image must be smaller than the screen (at most MM.HRES-1 by MM.VRES-1 pixels) and be an 8-bit RGB, RGBA, grey or grey with alpha PNG, or an indexed one; interlaced files are not supported.
If the file has transparency (an alpha channel, or an indexed file with a transparency chunk) the ‘transparency_cut_off’ parameter is used to determine whether each pixel should be solid or missing/transparent.  Valid values are 1 to 15, default is 8.  MMBasic compares the 4 most significant bits of the pixel's transparency with the cut off value: a pixel below it is transparent and the others are solid.  This allows RGB(0,0,0) to be a valid solid colour.  In the 32-bit colour depth the transparency values are kept as they are in the file.
A file without transparency (RGB or grey) is loaded with all its pixels solid.

=+= SPRITE MOVE
--- keep
Actions a single atomic transaction that re-locates all sprites which have previously had a location change set up using the SPRITE NEXT command.  Collisions are detected once all sprites are moved and reported in the same way as from a scroll.

=+= SPRITE NEXT [#]n, x, y
--- keep
Sets the X and Y coordinate of the sprite to be used when the screen is next scrolled or the SPRITE MOVE command is executed.  Using SPRITE NEXT rather than SPRITE SHOW allows multiple sprites to be moved as part of the same atomic transaction.

=+= SPRITE NOINTERRUPT
--- keep
Disables collision interrupts.

=+= SPRITE READ [#]n, x, y, w, h [,page]
--- keep
Reads the display area specified by coordinates ‘x’ and ‘y’, width ‘w’ and height ‘h’ into buffer number ‘n’.  If the buffer is already in use and the width and height of the new area are the same as the original then the new command will overwrite the stored area.
The optional parameter ‘page’ specifies which page is to be read to create the sprite.  The default is the current write page.  Set ‘page’ to FRAMEBUFFER to read from the framebuffer (see the FRAMEBUFFER command).

=+= SPRITE RESTORE
--- keep
Restores all the sprites hidden by SPRITE HIDE ALL.  Any position changes previously requested using SPRITE NEXT for sprites on layers other than 0 will be actioned by the RESTORE and collision detection will be run.

=+= SPRITE SCROLL x, y [,colour]
---
Scrolls the background and any sprites on layer 0 ‘x’ pixels to the right and ‘y’ pixels up.  ‘x’ can be any number between -MM.HRES/2-1 and MM.HRES, ‘y’ any number between -MM.VRES/2-1 and MM.VRES.
Sprites on any layer other than zero will remain fixed in position on the screen (or move to the position set by SPRITE NEXT).  By default the scroll wraps the image round. ---
Scrolls the region of the screen defined by the top left coordinates ‘x’ and ‘y’ and width and height ‘w’ and ‘h’ by ‘delta_x’ pixels to the right and ‘delta_y’ pixels up (each less than the width or height of the region).
By default the scroll wraps the background round.  If ‘colour’ is specified the colour will replace the area behind the scrolled image (-1 wraps it as the default does). # sprites.c SHOW: 7 or 9 arguments; x from 1-width to MM.HRES-1, y from 1-height to MM.VRES-1, layer 0 to 10
# (MAXLAYER), orientation 0 to 3.
=+= SPRITE SHOW [#]n, x, y, layer [,orientation]
---
Displays sprite ‘n’ on the screen with the top left at coordinates ‘x’, ‘y’ (part of the sprite can be off the screen: ‘x’ can be from 1 - its width to MM.HRES-1 and ‘y’ from 1 - its height to MM.VRES-1).  ‘layer’ is a number from 0 to 10.  Sprites will only collide with other sprites on the same layer, layer zero, or with the screen edge.  If a sprite is already displayed on the screen then the SPRITE SHOW command acts to move the sprite to the new location (and layer).  The display background is stored as part of the command and will be replaced when the sprite is hidden or moved further.
‘orientation’ is optional and can be:
{l=720}0 - normal display (default if omitted)
{l=720}1 - mirrored left to right
{l=720}2 - mirrored top to bottom
{l=720}3 - rotated 180 degrees (= 1+2)

=+= SPRITE SHOW SAFE [#]n, x, y, layer [,orientation] [,ontop]
---
Shows a sprite and automatically compensates for any other sprites that overlap it.
If the sprite is not already being displayed the command acts exactly the same as SPRITE SHOW.
If the sprite is already shown it is moved and remains in its position relative to other sprites based on the original order of writing.  ie, if sprite 1 was written before sprite 2 and it is moved to overlap sprite 2 it will display under sprite 2.
If the optional ‘ontop’ parameter is set to 1 then the sprite moved will become the newest sprite and will sit on top of any other sprite it overlaps.
Refer to SPRITE SHOW for details of the orientation parameter.

# CODE BUG: sprites.c SWAP skips a # before n2 with "if(*argv[2] == '#') argv[0]++" (argv[0] for argv[2]), so
# SPRITE SWAP 1, #2 is an error. The entry has b14's [#]n2: fix the code (argv[2]++).
=+= SPRITE SWAP [#]n1, [#]n2 [,orientation]
--- keep
Replaces the sprite ‘n1’ with the sprite ‘n2’.  The sprites must have the same width and height, ‘n1’ must be displayed and ‘n2’ must not be, or an error will be generated.  Refer to SPRITE SHOW for details of the orientation parameter.  The replacement sprite inherits the background from the original as well as its position in the list of order drawn.

=+= SPRITE TRANSPARENCY [#]n, transparency
--- keep
__IN THE 12-BIT COLOUR DEPTH ONLY__ Changes all pixels with a non-zero transparency in the stored sprite ‘n’ to the new level ‘transparency’, which can be between 1 and 15 (15 is solid).

# sprites.c WRITE: x from 1-width to MM.HRES, orientation 0 to 7, default 4. BlitShowBuffer with mode 4 also sets the
# sprite's x, y and reads the background into its store, so a WRITE of a displayed sprite replaces the background that
# SHOW stored (hence the last sentence).
=+= SPRITE WRITE [#]n, x, y [,orientation]
--- keep
Overwrites the display with the contents of sprite buffer ‘n’ with the top left at coordinates ‘x’, ‘y’.
The background that is overwritten is not stored so SPRITE WRITE is inherently higher performing than SPRITE SHOW but with greater functional limitations.  The optional ‘orientation’ parameter (0 to 7) defaults to 4 and specifies how the stored image data is changed as it is written out.  It is the sum of the following values:
